# 方针：云顶 Agent 的评测与调优

这份文档回答五件事：怎么证明 agent 是好的、benchmark 和 rubric 怎么建、调优怎么跑、能否迁移到其他赛季、能否接入实战。文中的数字都来自本仓库 `results/` 里的实际运行，复现命令见 README。

## 0. 目标与边界

**目标**：做一套可复现的评测与调优框架，用它把一个 LLM agent 从基线调到显著更强，每一步改进都有证据。

**不做**：不从零训练大模型；不把现版本天梯段位当作主目标（它是可选的最后一步，见第 8 节）。

面试时要讲的不是"我的 agent 多强"，而是"我怎么知道它变强了"。

## 1. 已经验证的事实

| 事实 | 数据 | 对方案的影响 |
|---|---|---|
| 环境能分出强弱 | 4 规则 bot + 4 随机 bot 同场 28 局：规则 bot 平均名次 2.76 ±0.11，随机 bot 6.24 | 评测工具本身可用 |
| 单局名次几乎是纯噪声 | 1 个规则 bot 对 7 个规则 bot，24 局：3.79 ±0.90（理论值 4.5），单局标准差 2.25 | 几十局的整局对比得不出结论 |
| 小差距在整局里看不见 | 把那个 bot 换成"20% 动作随机"的版本：4.08 ±0.90，两者区分不开 | 要把差距定到 ±0.3，每个版本约需 430 局 |
| 同种子配对没有用 | 两个版本在同一种子上的名次相关系数为 0.00 | 动作一旦不同，整局随机流就分叉；不能靠配对种子省局数 |
| 对局可以存档再续打 | 存档约 0.012 秒、恢复约 0.011 秒，每个 4.7 MB；从存档续打与原局逐座位一致（`tfteval/branching.py`）。之前的说法没有代码支撑，实际做时发现要先修一处座位顺序（README） | 决策题库可行，这是调优内环的基础 |
| 存档决定大部分名次 | 第 9/13/17 回合的 30 个存档各续打 20 次：名次方差 77% 由存档决定，同一存档内名次标准差 1.27（整局 2.25）；同一 k 的两个策略分叉名次相关 0.63 | 比较必须在存档内配对；平均差定到 ±0.3 约需 200–300 次续打，整局要 866 局 |
| 短视距血量+金币不是好答案 | 分叉后第 5 回合血量+金币与名次在同一存档内只相关 −0.38；`fast8` 比 `mimic` 少 7 点（几乎全是金币）而名次无差 | 它奖励不花钱，不能给经济题当答案 |
| 种子只在固定哈希种子时可复现 | 同进程内同种子结果一致，换进程不一致；固定 `PYTHONHASHSEED=0` 后一致。原因是座位名放在一个集合里，它的迭代顺序决定共用的商店随机流发给谁 | 运行脚本已强制固定 |
| 一局的规模 | 整局约 430 步（约 29 个回合）；每个座位平均约 370 个原子动作（约 25 个回合）；单核 14–39 秒，平均 21 秒 | 每个原子动作调一次模型不可行 |

仓库自带的"规则 bot 对随机"示例在当前提交上直接报错，自带的对局采集器在测试中不会结束。本仓库用自己的对局循环绕过，没有改动模拟器。

## 2. 什么叫"好 agent"

云顶是 8 人零和博弈：全场平均名次恒为 4.5，没有绝对分数。任何名次都必须同时说明对手是谁。所以"规则 bot 打随机 bot"不是 agent 好坏的证据，它只证明这套环境和统计能把强弱分开，并给出标尺最低的两级。

证明由四部分组成，缺一不可：

1. **对手梯子**。一组强度顺序事先已知的对手：`random` < `noisy50` < `noisy20` < `rule`（`noisyN` 是有 N% 动作随机的规则 bot）。对每一级跑"1 个 agent + 7 个该级对手"，报平均名次和 95% 区间。agent 的水平就是它在梯子上的位置。
2. **通过标准**。对梯子最高一级，名次区间的上界低于 4.5。梯子顶端之后要继续加高：agent 自己的历史版本进入对手池。
3. **没见过的对手和种子**。留一组调优期间从不使用的对手和种子，只在最后测一次。没有这一条，结论只是"对这几个 bot 调得好"。
4. **过程证据**。决策题得分上升、各类错误的发生率下降（第 3、4 节），并且这些变化能预测整局名次的变化。

主指标用 1 对 7 而不是 4 对 4：同一个 agent 的多份拷贝同场会抢同一批牌，互相拖累。这一点还没有实测，4 对 4 只用来做冒烟测试。

## 3. Benchmark：三层

| 层 | 内容 | 一次评测耗时 | 用途 |
|---|---|---|---|
| 决策题库 | 一个存档加一个决策点，选一个动作 | 分钟级 | 每个改动都跑 |
| 子环境 | 站位、装备的单场战斗（模拟器自带） | 分钟级 | 模块单测 |
| 整局梯子 | 第 2 节的对手梯子 | 小时级 | 里程碑才跑，是最终证据 |

**决策题怎么造**

1. 让梯子上的 bot 打整局，在决策点存档（要不要 D、要不要升人口、买哪张、装备给谁、怎么站）。
2. 对每个候选动作，从存档出发分叉续打 K 次，之后所有座位交给规则 bot 接管。
3. 比较各候选的结果。差距显著的题入库，差距不显著的丢掉。
4. agent 的得分是遗憾值：最优候选的期望结果减去它所选动作的期望结果。

**先做哪类题**。站位、装备、上哪个棋子这类决策，下一场战斗的胜负就是答案，标注便宜。经济类决策（D、升人口、存钱）影响的是十几个回合之后，用最终名次标注的话每个候选要几百次续打，太贵。经济题先只收差距很大的明显失误（差 1 名以上的题，同一存档约 8 对分叉就能标出来）。"几回合后的血量与金币"这类短视距指标已实测不可用：它把花钱算成损失（README"分叉有没有信号"）。这是全方案里最不确定的一环（第 9 节）。

**题库自身要验证**。题库得分的提升必须能预测整局名次的提升。先用梯子上的 bot 检验：`rule` 的题库得分应高于 `noisy20`，再高于 `noisy50`。顺序不对，说明题库是错的，先修题库。

**一个已知偏差**。标准答案的前提是"之后由规则 bot 接管"，所以它偏向规则 bot 的打法。agent 超过规则 bot 之后，要换成用 agent 自己续打来重新标注。

## 4. Rubric：只用在没有自动答案的地方

名次和遗憾值是算出来的，不需要 rubric。rubric 用来回答"为什么输"，即失败归因。

| 类别 | 例子 | 判定方式 |
|---|---|---|
| 执行 | 非法动作、回合内动作数用尽、计划与实际动作不符 | 日志规则 |
| 经济 | 无故低于利息线、连败时既不存钱也不 D | 日志规则 |
| 阵容 | 关键羁绊未激活、上场人数少于人口 | 日志规则 |
| 装备 | 成装给了非主力、散件长期积压 | 日志规则 |
| 站位 | 主力站前排、没有针对刺客调整 | 子环境反事实 |
| 决策理由 | 计划文字与局面事实矛盾、无视对手和牌池 | 模型判官加人工抽查 |

三条纪律：

- 能用日志规则判定的，不用模型判官。
- 模型判官上线前先人工标 50 条，算它与人的一致率，达标才用。
- 每一项都要检验"这项分数好，名次是否真的更好"。在梯子 bot 的对局上算相关性，不相关的项删掉。

## 5. Agent 的结构

每回合一次模型调用，输出一个带类型的计划：目标阵容、D 还是存、是否升人口、装备分配、站位模板。再由规则执行器把计划展开成原子动作。

- **为什么**：一局每座约 370 个原子动作，每个动作调一次模型的话，430 局约 16 万次调用。每回合一次是约 25 次每局，430 局约 1.1 万次。
- **附带好处**：每次调用都是一条可记录、可重放、可出题的决策。
- **最大的变量是观测的写法**：把局面写成什么样的文字，对结果的影响通常比提示词措辞更大，要当作一等公民来做消融。
- **记录要求**：固定模型版本，记录每次调用的输入输出，缓存响应以便重放。

`tfteval/policies.py` 里的 `LLMPolicy` 是这个接口的占位，尚未实现。

## 6. 调优循环

**内环，每个改动都跑，分钟级**

- 重放：改完提示词，对历史对局里的同一批局面重新提问，只看决策变了的地方。
- 决策题库：遗憾值有没有下降。

**中环，内环通过才跑，十分钟级**

- 从同一批存档出发，新旧版本用同一组重新播种的随机数各续打到终局，比较名次。存档共享了此前的全部运气，这是这里真正能消掉噪声的手段。不要只续打几个回合比血量和金币：实测这个指标奖励存钱，会把名次上没有差别的经济改动判成显著变差。

**外环，里程碑才跑，小时级**

- 整局梯子，局数按 `tfteval.stats.games_needed` 事先算好，不看着结果加局。

**纪律**

- 一次只改一处。
- 改之前写下预期哪项指标会动。事后对不上，就是理解有误。
- 题库和种子分成开发集与保留集，保留集只在最后用。
- 每次改动留一条记录：改了什么、内环分数、中环差值、是否进外环。这份记录就是面试材料。

## 7. 小模型加规则

方向是对的，顺序很重要：

1. 规则执行器加大模型做计划（第 5 节）。
2. 用题库和对局积累"局面、候选动作、标准答案"数据。
3. 把选项固定、频率高的决策蒸馏到小模型，输出带校准概率的类型化决策；置信度低时交给大模型。
4. 最后才考虑强化学习。

小模型的真正价值在统计上：它便宜到可以打几千局，整局评测才变得可靠。先做评测再训模型的理由是，没有第 3 节的题库，训出来的模型好不好无从判断。

### 能不能超过老师

取决于训练信号从哪里来。

| 信号来源 | 上限 |
|---|---|
| 老师的动作（蒸馏、模仿） | 老师。通常略低；把老师多次采样的结果取多数，可以比老师单次发挥稳一点，仅此而已 |
| 环境的结果（续打出的名次、战斗胜负） | 不受老师限制 |

本方案的题库答案来自"候选动作加续打"，不是老师的意见，所以超越的通道从一开始就是开的。循环是：当前策略提出候选，续打选出比它自己会选的更好的动作，用这些动作训练或改提示词，得到更强的策略，再用它重新标注。

这个循环有四个天花板，每个都要单独处理：

- **候选覆盖**：最优动作不在候选里，续打也选不出来。候选不能只由被测模型提出，要混入规则生成的和随机的候选。
- **续打策略**：现在由规则 bot 接管续打，答案偏向规则 bot 的打法。agent 超过规则 bot 之后，必须换成当前最强的 agent 来续打。
- **对手池**：零和博弈里"最优"是相对对手而言的。对手不变，学到的只是怎么打这几个 bot。历史版本要进对手池。
- **模拟器**：超出老师的那部分，可能是真本事，也可能是模拟器漏洞。新出现的打法要人工看回放确认。

只调提示词、不训练模型时还有一层上限：基础模型的推理能力。把续打做成它能调用的工具，等于给它加了搜索，这是不训练模型也能越过这层上限的办法。

这一小节是推理，还没有任何实测支持。

## 8. 跨赛季迁移与实战

**能迁移的**：评测框架和统计方法、题库的生成方法、rubric 的结构、"计划加执行器"的架构、利息与人口这类多年未变的机制知识。

**不能迁移的**：英雄、羁绊、装备数值、阵容知识，以及在 S4 上训出的任何小模型权重。强化符文是 S6 才加入的，S4 环境里完全没有这类决策。

**前提**：新赛季要有模拟器。目前我只找到 S4 的开源模拟器。Riot 自己的做法是用神经网络预测战斗结果来代替完整模拟（GDC 2023）。在只有一个赛季的模拟器时，迁移实验做不了，只能在设计上预留：把赛季知识做成可替换的知识包，与决策逻辑分开。

**实战**放在最后，可选：

- 自动操作客户端违反用户协议，有封号风险，不建议。
- 建议型（人操作，agent 给建议）风险低得多，但第三方工具的边界要先查清楚。
- 段位同样受第 1 节的噪声支配，需要几百局才稳定，还要补齐现版本知识。
- 对面试来说，实战段位不是必需的证据。

## 9. 风险与未知

按我没把握的程度排序：

1. **大模型基线有多强**。没有测过，可能连规则 bot 都打不过。这决定项目的起点。
2. **规则 bot 相当于什么水平的人**。不知道。如果它很弱，"超过规则 bot"说明不了多少，梯子必须靠 agent 的历史版本继续加高。
3. **经济类决策题能否便宜地标注**（第 3 节）。可能需要先训一个"局面到最终名次"的预测模型当标注器。
4. **题库得分与整局名次是否相关**。不相关的话题库要重做。
5. **模拟器的保真度**。S4 战斗是否忠实于原游戏没有核对过；自带示例已坏说明维护状态一般。调优有可能学到的是模拟器的漏洞。
6. **跨机器复现**。只在一台机器、Python 3.13 上验证过。

容易漏掉的：

- 调了几十轮之后，提示词会悄悄适配开发集的种子和对手。保留集是唯一的防线。
- 模型供应商会更新模型，同一个提示词的行为会变。要固定版本并留存响应。
- 调用的限速和预算要提前算，430 局是按每个版本算的。
- 模拟器是 Apache-2.0 许可，可以使用和修改，需保留声明。游戏内容属于 Riot，公开仓库前确认其对非商业同人项目的政策。
